# Бэкенд Supabase — источник истины в репозитории сайта

Схема базы данных, миграции и Edge Functions **больше не хранятся в этом
репозитории**. Единый источник истины:

```
D:\Project\Auto RS Website\supabase
```

Там лежат:

| Путь | Что это |
| --- | --- |
| `migrations/` | Миграции 0001–0066 и все последующие |
| `checks/` | Проверочные скрипты к отдельным миграциям |
| `functions/` | Edge Functions (`daily-cleanup`, `send-push`) |
| `full_schema.sql` | Полная схема одним файлом |
| `DEPLOY.md` | Инструкция по развёртыванию с нуля |

## Нумерация миграций продолжается с 0067

Последняя миграция, переехавшая отсюда, — `0066_bucket_listing_authenticated_only.sql`.
Все новые миграции, **начиная с 0067**, создаются только в репозитории сайта.

Заводить миграции здесь нельзя: два независимых счётчика в двух
репозиториях рано или поздно дадут два разных файла с одним номером, и
порядок применения станет неопределённым.

## Почему так

Сайт — полноценный продукт и источник истины по схеме и дизайну
(см. `CLAUDE.md` в репозитории сайта). Приложение — второй клиент того же
бэкенда: оно использует те же таблицы и те же RPC, но не владеет ими.

## Что делать разработчику приложения

* **Нужно посмотреть схему или RPC** — открыть файлы по пути выше.
* **Нужна новая таблица, колонка или RPC** — миграция создаётся в
  репозитории сайта и применяется оттуда же (`supabase db push`).
* **Приложение сломалось после изменения схемы** — сверяться с
  миграциями сайта; вызовы RPC из приложения не должны ломаться, это
  требование к новым миграциям.

## Служебный каталог `.temp`

`.temp/` остаётся здесь и в git не попадает (`.gitignore`). Это локальный
кэш Supabase CLI. Связь CLI с проектом настроена и в репозитории сайта —
работать с базой следует оттуда.
